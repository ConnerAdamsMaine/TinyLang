# TIDE Governance

TIDE makes project decisions traceable without rewriting the request that motivated them. The original request and author remain associated permanently; later amendments, evidence, decisions, implementation, and verification are separate ledger events or records.

Users can create immutable records, nested replies, amendments, and relationships. Maintainers can append decisions with rationale, select a separate resolution record, set a supported derived status, attach implementation references, add verification and policy events, and update each immutable `TIDE-XXXXXX/Rn` requirement reference with a rationale-backed lifecycle event. Requirement history is append-only and the detail view projects the latest status per requirement. Marking an overall request Satisfied requires every submitted reference and every requirement's latest lifecycle state to be Satisfied; reopening the record is required before changing an individual satisfied requirement. Maintainers can grant or revoke developer, tester, and reviewer roles; authorized implementation and verification events record the applicable role. A dedicated reconsideration interface and additional contributor roles remain unimplemented. A new record and each requirement start Active; that label is not approval.

Financial sponsorship does not grant engineering votes, moderation authority, priority, attribution, or an exemption from policy. The previously discussed TinyLang v2 proposals are unpublished and must receive identifiers only if and when their authors submit them through TIDE.
