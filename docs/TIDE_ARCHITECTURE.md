# TIDE Architecture

TIDE currently runs inside the existing `Web` Rust/Axum application and PostgreSQL database.

- `Web/src/tide.rs` implements category and paginated record/reply/event listing, record creation and lookup, nested discussion replies, append-only governance events, event-chain verification, ID format validation, and the signed-in user's public TIDE identity.
- `Web/src/x.rs` implements X account linking and sign-in for existing linked identities with OAuth 2.0 authorization code, PKCE (S256), and short-lived state/verifier storage. GitHub and Discord provide the same linking and sign-in behavior.
- `Web/src/tickets.rs` implements private ticket creation, owner-scoped listing and reading, threaded replies, staff-only notes, support-agent assignment, status transitions, and audit history.
- `Web/src/investigations.rs` implements private user reports, investigator-only case/evidence access, append-only reviews, one-human suspension decisions, and two-distinct-reviewer permanent-ban decisions.
- `Web/src/appeals.rs` implements email-verified single-use appeal links, appeals bound to the active TIDE enforcement action, two-matching-reviewer independent decisions, and transactional reversal.
- `Web/src/chat.rs` implements authenticated public/private channel access, public channel-ID resolution through the same visibility filter, one-to-one and fixed-membership group direct messages, persistent history and search, rate-limited mentions, PostgreSQL cross-instance message fan-out, reactions, replies, user deletion, abuse reporting, and 90-day cleanup.
- `Web/src/contributors.rs` implements maintainer-managed append-only contributor roles, current-role lookup, and public grant/revocation history.
- `Web/src/notifications.rs` keeps TIDE workflow alerts in the existing account inbox; its transactional summaries omit private support messages, investigation evidence, and review rationales.
- `Web/src/main.rs` mounts the routes under `/api/v1`.
- `Web/migrations/0010_tide_core.sql` installs allocators, user IDs, categories, record/event/reply/relationship storage, indexes, and append-only triggers for original records and events. `0011_tide_event_order.sql` adds serialized event positions for deterministic chain verification. `0012_tide_support.sql` adds explicit support-agent grants, ticket storage, messages, and append-only ticket history. `0013_tide_investigations.sql` adds investigator grants, private case/evidence/review storage, and append-only case events. `0014_tide_appeals.sql` adds exact-action enforcement linkage and private appeal/token/review/event storage. `0015_tide_chat.sql` adds channels, memberships, time-limited messages, reactions, moderators, and reports. `0016_tide_requirement_status.sql` extends the append-only event type set for per-requirement lifecycle events. `0017_tide_contributor_roles.sql` adds append-only contributor-role grants and revocations. `0018_tide_notifications.sql` extends the existing inbox to cover TIDE workflows. `0019_tide_nested_replies.sql` adds same-record parent relationships for nested discussion replies. `0020_tide_chat_search.sql` adds a trigram index for bounded chat substring search. `0021_tide_chat_mentions.sql` enables inbox notifications for channel mentions. `0022_tide_chat_direct_messages.sql` creates idempotent one-to-one private chat channels. `0023_tide_linked_identities.sql` stores globally unique linked provider subjects. `0024_tide_chat_blocks.sql` adds direct-message blocking. `0025_tide_x_identity.sql` enables X identities and short-lived X PKCE state. `0026_oauth_pkce.sql` adds transient verifier storage to the existing GitHub and Discord state tables. `0027_provider_sign_in.sql` allows OAuth state to represent either a signed-in account-link request or an unauthenticated provider sign-in request. `0028_tide_ticket_attachments.sql` adds PostgreSQL-backed private ticket attachments, resolution timestamps, and attachment event types; a background task purges attachment bytes 90 days after continued resolution while retaining metadata. `0029_tide_chat_group_directs.sql` adds group direct-message rosters with canonical, unique participant-set keys. `0030_account_recovery_codes.sql` stores hashes of one-time account-recovery codes and enforces their single-use state transition. `0031_tide_investigation_attachments.sql` stores private immutable evidence-file metadata/content and supports scheduled byte purging after case closure.
- `Web/public/tide.html` and `Web/public/tide.js` provide the category, submission, nested reply, event, decision, implementation, verification, and integrity-check UI. `Web/public/support.html` and `Web/public/support.js` provide ticket creation, private conversations, status updates, support-agent controls, and bounded private attachment upload/download/deletion. `Web/public/investigations.html` and `Web/public/investigations.js` provide private reporting and investigator review controls. `Web/public/appeals.html` and `Web/public/appeals.js` provide public appeal-link requests/submission and investigator review controls.
- `Web/public/chat.html` and `Web/public/chat.js` provide channel selection, one-to-one and group direct messages, WebSocket chat, reconnect, history, search, mention/direct-message notifications, replies, reactions, and message reports.
- GitHub, Discord, and X identity links are stored in `tide_identity_providers`; linking and sign-in flows use PKCE (S256), with short-lived state and verifier data persisted only until callback completion. Sign-in flows bind OAuth state to the initiating browser with a short-lived HTTP-only SameSite=Lax cookie. Provider sign-in accepts only an already linked identity on an active, unsuspended account and does not create or link accounts. TIDE forum, ticket, investigation, and chat write actions require a session established by a supported OAuth provider that is linked to the same TIDE identity. GitHub remains the separate source for repository contributor synchronization.

Request creation uses the existing Web per-IP forum posting rate limiter and the application's global body limit. TIDE-specific per-user quotas have not been added. Forum search uses a generated weighted PostgreSQL `tsvector` over titles, original content, and rationale with a GIN index; request listing supports category, record type, current tag, full-text query, and newest/oldest ordering. Tag assignment/removal is represented by append-only `TAG`/`UNTAG` events in the same hashed ledger as decisions and implementations. Category moderator grants/revocations are separately recorded in an append-only event table; category moderators can append hashed reply-lock events, and new replies serialize against moderation events. Authenticated maintainers can add categories or update definitions through the TIDE category API; stable slugs cannot be renamed, categories are not deleted, and every administrative change records immutable before/after state and rationale in `tide_category_definition_events` (`0039_tide_category_definition_events.sql`). Category history is publicly readable.

The database allocates independent user, forum, ticket, channel, and investigation namespaces. User, forum, and ticket public identifiers are used. Existing account UUIDs are preserved; new accounts and TIDE record, reply, relationship, event, and ticket UUIDs use UUIDv7.

Canonical request content is serialized server-side and SHA-256 hashed. Events have a separate SHA-256 integrity hash and previous-event references. The database rejects UPDATE/DELETE on TIDE original records and events. A public integrity endpoint recomputes the original-content hash and verifies event hashes and chain links. An optional Compose backup profile streams full PostgreSQL custom-format dumps through age encryption, signs the encrypted artifact manifest with minisign, and uploads to a versioned S3-compatible bucket with COMPLIANCE Object Lock retention. The backup includes private database tables and must be treated as sensitive; the decryption identity is not mounted in the backup worker. Deployment must configure and verify an external bucket and periodically exercise the restore utility; no live production-bucket recovery exercise or load benchmark has been performed. TIDE contributor roles currently govern implementation and verification evidence; other TIDE role types remain separate explicit grants.

Migration `0032_tide_provider_sessions.sql` records the provider that established each session; existing sessions and local password/recovery sessions are marked `local`. TIDE write paths require the current authenticated session to be GitHub, Discord, or X OAuth and require that exact provider to be linked to the account. `0033_tide_forum_search.sql` adds the generated full-text search vector and GIN index; `0034_tide_investigator_conflicts.sql` adds permanent conflict disclosures and recusal; `0035_tide_record_tags.sql` enables append-only tag events; `0036_tide_category_moderators.sql` enables category-scoped moderator assignments and moderation ledger events; `0037_tide_duplicate_detection.sql` installs the trigram extension, disabled-login detector identity, and append-only detection-signal storage; `0038_tide_github_webhook_deliveries.sql` adds append-only delivery idempotency records for verified merged-PR implementation events; `0039_tide_category_definition_events.sql` adds immutable, rationale-backed before/after history for maintainer-managed category definitions; `0040_tide_submission_burst_signals.sql` extends append-only signals to cover rapid submission bursts without claiming a similarity score; `0041_tide_conflict_adjudication.sql` adds append-only independent conflict assessments that require two matching investigator votes and never lift recusal; `0042_tide_ban_evasion_signals.sql` extends the signal rules to a content-only possible-ban-evasion lead (new accounts reposting a restricted account's content) while allowing single-record matches. New request and governance event attestations include the current session provider plus the linked provider types, but never provider subject IDs or OAuth tokens.

Support agent, investigator, and chat moderator access are controlled by explicit grant tables; neither follows from general administrator or moderator roles. Ticket, investigation, and appeal state changes use transactions; private messages/evidence do not enter the public governance ledger. Investigators may append a conflict disclosure; it is shown to investigators and locks the declaring investigator out of subsequent case evidence, review, adjudication, and appeal actions. Independent, eligible investigators may append conflict assessments; two matching votes finalize the assessment, but never lift recusal or rewrite the declaration or earlier case decisions. Case locks serialize conflict declarations/adjudications and investigator/appeal actions. Near-duplicate, rapid-submission-burst, and content-only possible-ban-evasion detectors create private, unreviewed investigations and cannot enforce restrictions; broader governance-manipulation and coordinated-abuse detection patterns remain incomplete. Permanent bans from TIDE require two distinct investigator reviews. Appeal outcomes require two distinct eligible investigators to agree; split votes leave the appeal open and do not change the restriction. Appeal links are sent only to verified account email, expire after 30 minutes, and cannot clear an administrative restriction that superseded the TIDE action. One-to-one direct-message channels are accessible only to their two participants; group direct messages are accessible only to their fixed member roster. Moderators are excluded from both direct-message types. Chat uses PostgreSQL notifications for multi-replica fan-out; a two-container end-to-end harness (`Web/tests/chat-multi-replica/run.ps1` with `docker-compose.multi.yml`) verifies a message posted to one real web replica reaches a WebSocket client connected to the other, while load and browser end-to-end behavior at capacity remain unverified. Ticket attachments are stored in PostgreSQL; their bytes are purged after 90 days of continuous resolution while digests and metadata remain. Database tests cover expiry, recent-resolution retention, reopened tickets, and idempotent cleanup. Disposable-PostgreSQL tests cover ticket attachment authorization/audit and retention, group direct-message privacy, OAuth provider callback exchanges with local mocks, recovery concurrency, investigation evidence authorization and retention, conflict recusal and independent adjudication, all three automated detection rules, category moderator controls and maintainer-managed category definitions, reviewer thresholds, split and matching appeal votes, cross-instance chat fan-out, and investigator grant revocation locking. A configured GitHub pull-request webhook verifies HMAC signatures and repository identity, enforces current linked-author developer/maintainer authorization, appends implementation evidence atomically, and deduplicates delivery retries. Broader attachment workflows, live OAuth provider registrations, chat WebSocket/browser load behavior, recovery without a verified email or code, email delivery, further detection patterns, and automatic record/PR synchronization outside merged-PR body markers remain incomplete. Implementation evidence references are checked against GitHub before append.
