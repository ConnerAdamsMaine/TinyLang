# TIDE Identities

The Web migration assigns each existing account a permanent `TIDE-U-XXXXXX` public ID and makes the ID column unique and non-null. Existing accounts are assigned in creation-time/UUID order; new registrations use an atomic PostgreSQL namespace allocator. IDs use six uppercase Base36 characters and are never recycled by the allocator. Identity remains attached to the existing account rather than its username or email.

TIDE User IDs appear on public member profiles, forum records and replies, chat messages, and contributor-role history. Use the ID to reference a person across username or provider-name changes.

TIDE participation requires a session established by GitHub, Discord, or X OAuth, and the selected provider identity must already be linked to that same TIDE identity. Linking a provider from an existing website session does not convert that local session into an OAuth-authenticated session; the user must sign in through the linked provider before participating. OAuth login never creates an account or links an identity automatically. All three providers use one-time, expiring authorization-code flows with PKCE (S256); sign-in state is also bound to the initiating browser with a short-lived HTTP-only SameSite=Lax cookie. Verifiers are stored only until callback completion, and provider flow starts are rate-limited per client IP. Localhost-mocked integration tests exercise all three callback exchanges, provider identity validation, PKCE verifier submission, and one-time callback state; these tests do not verify production provider registrations or live provider behavior. Each provider ID is unique across TIDE identities; the provider username is display metadata, not an identity key. Access tokens are discarded after identity verification. GitHub remains the separate source for repository contributor synchronization.

Limitations: Google and Microsoft are not implemented. Accounts retain local passwords and verified-email password reset. Account settings allow users to generate ten high-entropy recovery codes after re-entering their password; the plaintext codes are shown once, and generating a replacement set invalidates unused codes. A recovery code can be used once to set a new password and email address, revoke existing sessions, and start email verification for the new address. The account can be signed into after recovery, but the new address must be verified before posting or using other email-verified features. Users should store these codes offline; anyone who obtains an unused code can recover the account. Account-link management is available on the account page. New user and TIDE resource UUIDs are UUIDv7, while existing accounts retain their original internal UUIDs. Security-event workflows are not implemented.

The event records include the TIDE user ID, the provider used to establish the current session, the verified-linked-identity participation requirement, and the provider types linked to that account at submission time. This is a server-side attestation, not a personal cryptographic signature. OAuth tokens and provider subject IDs are not copied into TIDE event payloads. Existing sessions are classified as local when the migration runs and must be replaced by a provider sign-in for TIDE participation.
