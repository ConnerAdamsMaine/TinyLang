# TIDE Overview

TIDE (TinyLang Intent & Decision Engine) is the new official destination for TinyLang requests and engineering governance. Its governing principle is to preserve an author's original request while allowing later evidence and decisions to coexist with it. It supersedes the previously planned TLR/TLP/TLIN submission workflow; it does not rename the TinyLang Runtime abbreviation where that term is independently used.

The Web application is an existing Rust/Axum and PostgreSQL modular monolith. The first TIDE implementation adds a separate `/api/v1` surface, persistent TIDE user IDs, official category definitions, append-only record and event tables, SHA-256 content/event hashes, and a static TIDE interface. Existing forum records are not rewritten or assigned TIDE IDs.

Read [TIDE identities](TIDE_IDENTITIES.md), [forum categories](TIDE_FORUM.md), [request behavior](TIDE_REQUESTS.md), and [deployment notes](TIDE_DEPLOYMENT.md).

## Current implementation boundary

New records can be submitted by users whose current session was established through a linked GitHub, Discord, or X OAuth identity. Merely linking a provider to a local-password session does not qualify. Original content, author, category, type, requirements, timestamps, and content hash are retained. Each new record receives a database-allocated `TIDE-XXXXXX` identifier and a `REQUEST` event. The API also supports append-only amendments, relationships, maintainer decisions, implementation evidence, verification reports, policy events, and auditable tag changes. When configured, a signed GitHub pull-request webhook appends implementation evidence for marked TIDE records on merged PRs by authorized linked contributors. Decision status is projected from the latest decision event; marking a request satisfied requires references to every submitted requirement. Event history has a hash-and-chain verification endpoint. Forum browsing supports PostgreSQL full-text search and category, record-type, tag, and date-order filters.

This remains a partial implementation, not the TIDE v1.0 definition of done. GitHub, Discord, and X account linking and sign-in for identities already linked to an existing account are implemented; OAuth never creates or links accounts automatically. TIDE writes now require that the current session was established by the same linked provider. Account owners can recover access without their old verified email using a one-time recovery code, set a new password and email, and verify the new email before posting or using other email-verified features. X linking and sign-in use PKCE and the minimal `users.read` scope. Existing local-password accounts can also recover from lost linked providers through verified-email password reset, then link a replacement. Each immutable request requirement now has an append-only status history and a latest-status projection; overall satisfaction requires every requirement to be marked satisfied. Contributor role grants and revocations are append-only; maintainers can assign developer, tester, and reviewer roles, which authorize and are recorded on implementation and verification events. Forum records support up to 20 append-only tags and category-scoped moderator assignment with auditable reply locking. The existing private inbox now includes TIDE record replies/events, support responses and status/assignment changes, investigation status updates, appeal outcomes, chat mentions, and direct-message notices. Private notices contain summaries and links only; internal support notes and private investigation evidence are not copied into inbox content. Chat provides authenticated public channels, one-to-one and fixed-membership group direct messages (up to 10 participants), one-to-one blocking, bounded WebSocket messaging, history, replies, reactions, search, mentions, deletion, reporting, cross-instance fan-out via PostgreSQL (verified end-to-end with two real web replicas in Docker, including a live browser pass across both replicas), and 90-day retention; capacity/load testing at scale remains open. TIDE discussion supports nested replies, while reply editing/deletion is not implemented. Private support tickets have owner-scoped access, designated support-agent access, messages, internal notes, assignment, status history, and PostgreSQL-backed PDF/PNG/JPEG/plain-text attachments with bounded upload, authorized downloads/deletion, and 90-day post-resolution byte purging; owner/staff isolation, assignment/status auditing, attachment retention, investigation visibility/evidence retention, conflict recusal and independent conflict adjudication, duplicate detection, permanent-ban review, appeals, account recovery, OAuth session provenance, category moderator reply controls, and investigator-revocation locking have disposable-PostgreSQL integration coverage. Conflict adjudication requires two matching independent votes and never lifts recusal or changes a prior decision. Near-duplicate, rapid-submission-burst, and content-only ban-evasion detectors create private non-punitive investigation leads; the ban-evasion rule only catches new accounts reposting an actively restricted account's content and cannot see account relationships, so coordinated governance-abuse and broader ban-evasion detection remain incomplete. OAuth callback flows have local-mock coverage, but live provider registration and callback verification remain untested. An optional S3-compatible full-database backup worker encrypts dumps before disk staging, signs manifests, and applies Object Lock retention; live external-bucket configuration and restore rehearsal are still unverified. Browser end-to-end behavior and load testing at capacity also need a staging deployment. See each subsystem guide for its actual state.

The previously discussed TinyLang v2 proposals remain unpublished drafts. None has been migrated, assigned an identifier, or represented as accepted or implemented history.
